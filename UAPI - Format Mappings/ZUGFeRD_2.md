# UAPI v6 → ZUGFeRD 2 (EN 16931 profile, CII)

As of 2026-11-16 · Status: draft for review

UAPI v6 invoice and correction fields mapped to ZUGFeRD 2 / Factur-X, EN 16931 (COMFORT) profile: CII XML inside a PDF/A-3 file. A DE supplier's invoice becomes ZUGFeRD when its one BUSINESS recipient has `invoicing.type` `EMAIL` (the default for a DE address) with `invoicing.format` `ZUGFERD_V2` or none. The format is kept only for a DE address (`RH`:3366-3369), so `XRECHNUNG_V3` to a BE address also yields ZUGFeRD, without an error. An SDI block from a DE supplier is typed ZUGFeRD too (`E/invopop.go:300-313`) but has no workflow (§6.1). The CII XPath column is the spec target from the locally pinned Factur-X 1.08 / ZUGFeRD 2.4 field table (sheet "Factur-X CII D22B EN16931"). In force since 2026-09-01 is ZUGFeRD 2.5.2 / Factur-X 1.09.2: 2.5 updated the code lists and validation artefacts (FeRD press release 2026-06-10), and 2.5.2 renamed BR-CO-27 to CII-SR-470. The full change log is behind a registration form, so the 1.09.2 rule set is UNVERIFIED. UAPI paths are relative to `content.operation` ([UAPI_v6_Fields.md](UAPI_v6_Fields.md)). The UAPI column names the field whose meaning is that BT (the target mapping); `NEW field needed` marks a field UAPI lacks, and today's behaviour is in the notes.

**Citations:** `G/` = fiskaly `src/unified/einvoicing/gobl/`, `E/` = `src/unified/einvoicing/`, `RH` = `src/unified/api/v6/record_handler.go`, `EA` = `src/unified/domain/record/einvoicing_adaptations.go`, `W` = `src/unified/worker/e_invoicing_worker.go`, `SV1` = `src/unified/domain/record/service_v1.go`, `WF` = `cmd/invopop-workflow-migration/workflows/DE_SEND_INVOICE_EMAIL_ZUGFERD_BUSINESS.json` (all `fiskaly/meta@cd19ec8`); `gobl/` = invopop/gobl v0.501.0, `gobl.cii/` = v0.81.0, `gobl.de.xinvoice/` = v0.0.9. `FX-SCH-A-nnnnnn` = assert ID in the Factur-X 1.08 `FACTUR-X_EN16931.sch`; `BR-…` = EN 16931 rule ID.
